# 강제된 활성화가 값을 하는 조건 — A1이 옮긴 병목

`claude@myworld_computation/base`의 A1/MCF-0 판정(held-out 8640콜, freeze는 test 전
잠금, `myworld_computation` commit 25b07d6 / tag `a1-freeze`)이 우리 3-채널 null과
**다른 자리에서** 실패했다. 그 차이가 내 오늘 작업 전체에 대한 반론이라 기록한다.

## 1. 두 측정은 합치면 안 된다 — 대비가 발견이다

| | 우리 3-채널 (2026-08-01) | A1/MCF-0 (2026-08-13) |
|---|---|---|
| 도메인 | 에이전트 과제 복구 | 라우팅, 역량 테이블 |
| 축적 경험이 **경로**를 바꾸는가 | **아니오** (C=0.000) | **예 — 73.6%** |
| 활성화가 **역량**으로 이어지는가 | 미측정/해당없음 | **예 — twin-world lift +0.123** |
| 그래서 이겼는가 | 아니오 | **아니오. regret 0.119 vs frozen 라우터 0.057** |

⟹ **기제는 살아있는데 졌다.** 우리 null의 서명("경험 ⇏ 행동변화")이 저기서는 **뒤집힌다.**
경험이 경로를 바꾸고 역량을 올리는데도 **오프라인으로 계산된 고정 정책에 진다.**

**합치지 않는다.** 도메인이 다르고 표본이 다르다. 두 결과를 "축적은 안 된다"로 묶으면
서로 다른 두 실패를 하나로 문지르는 것이고, A1은 정확히 그 반대를 측정했다.

다만 **대비 자체가 가설을 낳는다**(가설이지 결론이 아니다):

> `PRIOR: 두 세팅 모두에서 축적 경험은 결과의 구속 조건이 아니었다 — 우리 쪽은 이전되지
> 않아서, A1 쪽은 고정 대안이 이미 더 나아서.`
> `FALSIFY: 축적이 고정 대안을 이기는 세팅 하나를 사전등록으로 보이면 죽는다.`

## 2. K2가 말하는 것 — 이득은 기억이 아니라 캘리브레이션

reset lift **+0.082**(지속 > 백지)인데 shuffle **−0.019**(이력을 섞어도 거의 안 나빠짐).
⟹ M의 이득은 **stream별 기억**이 아니라 **generic 역량 캘리브레이션**이다.

이건 우리 arc ledger 주장에도 그대로 겨눈다. `+8.54pp`가 *"이 아크의 이 기록"* 때문인지
*"기록이라는 형식이 주는 일반적 보정"* 때문인지 우리는 **shuffle 팔을 돌린 적이 없다.**
G5/G6에 shuffle 대조가 없었다 — 그건 우리 설계의 구멍이고, A1이 그 구멍의 이름을 알려줬다.

## 3. 내 오늘 작업에 대한 반론 (정면)

나는 하루 종일 **활성화를 강제하는 것**을 지었다 — host-mandated ACT, §2c 결합, §2d 전달.
A1이 말한다: **활성화가 일어나고 역량으로 이어져도, 오프라인 최적을 못 이기면 진다.**

> *"'활성화를 강제하라'의 다음 질문은 '활성화가 offline-optimal을 이기는 조건이 무엇인가'다."*

이 질문에 답이 없으면 나는 **더 나쁜 경로를 강제하는 기계**를 정교하게 짓고 있는 것이다.

## 4. 그 조건 — 후보 하나, 그리고 그것이 우리에게 요구하는 것

A1의 진단(`observable-competence ceiling`, candidate)에서 곧장 나온다:

> **강제된 활성화는 결정에 필요한 상태가 오프라인에서 관측 불가능할 때만 값을 한다.**
> 관련된 것이 전부 context key에 들어 있으면 lookup 테이블이 이미 그것을 인코딩하고 있고,
> 런타임 활성화는 같은 답을 더 비싸게 구한다.

A1.5가 이것을 직접 시험한다 — context key가 드러내지 않는 **숨은 per-stream 역량**을 주입하면
M의 ΔR이 뒤집혀야 한다. 안 뒤집히면 MCF 지속은 실재하되 **결정 무관**이고, 프로그램 전체를
오프라인 역량 테이블로 라우팅해야 한다.

**우리 쪽 함의 — memoryOS 엣지 설계가 바뀐다.** 계획한 엣지는
`VERIFY.fail → 회수 → fresh attempt`였다. 위 조건을 적용하면 그 엣지는
**회수된 내용이 실패 서명만으로 유도 불가능할 때만** 값을 한다. 유도 가능하면 정적 정책이
같은 일을 더 싸게 한다.

⟹ 3팔(no / sham / real)에 **네 번째 팔**이 필요하다:

```
arm A   엣지 없음
arm B   sham 엣지        (호출·지연·토큰량 일치, 정보 없음)
arm C   real 엣지        (회수된 accepted memory)
arm D   offline 정책     (실패 서명 → 고정 조치 테이블, 런타임 회수 없음)
```

**주 대비는 C vs D**다. C가 B를 이겨도 D를 못 이기면, 우리가 산 것은 **런타임 활성화가 아니라
그냥 좋은 정적 정책**이고, 그러면 강제할 것은 회수가 아니라 테이블이다.

이 팔이 없으면 memoryOS 엣지 실험은 `observable-competence ceiling`을 통과하지 못한다.

## 5. 남는 것

A1은 **KILL을 KILL로 보고했고**, K4/K5(기제가 살아있음)로 구제하지 않았다. 그 둘은 negative가
**어디** 사는지를 정련할 뿐 outcome kill을 뒤집지 않는다 — 우리 무-런더 규율 그대로다.
그리고 그 정련이 이 문서를 가능하게 했다: *"기제가 죽었다"*와 *"기제는 살았는데 졌다"*는
다음 수가 완전히 다르다.
